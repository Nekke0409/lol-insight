# ADR-001: Use Modular Monolith for Initial Architecture

Status: Accepted

## Context

이 프로젝트는 다음 기능을 순차적으로 구현한다.

1. Riot Games API 기반 플레이어 검색 및 전적/통계 조회
2. 플레이 데이터를 기반으로 한 AI 분석 및 피드백
3. 사용자 계정과 게시글/댓글을 포함한 커뮤니티

기능 영역은 서로 다르지만 현재는 단일 개발자가 학습 목적으로 개발하는 초기 단계다.

초기부터 기능별 서비스를 독립 배포하는 마이크로서비스 구조를 사용하면
서비스 간 통신, 분산 트랜잭션, 배포, 관측, 장애 처리 등
현재 핵심 문제와 직접 관련이 없는 복잡도가 크게 증가한다.

반대로 하나의 애플리케이션에 모든 코드를 경계 없이 배치하면
Riot API 연동, Match 처리, AI 분석, 커뮤니티 기능이 성장하면서
의존성이 뒤섞일 가능성이 있다.

## Decision

초기 Backend는 **하나의 Spring Boot 애플리케이션으로 배포하는 Modular Monolith**로 구성한다.

하나의 프로세스와 배포 단위를 유지하되,
Player, Match, Analysis, Community 등 기능 영역의 경계를 코드 구조에서 명확히 유지한다.

코드 구성은 package-by-feature를 우선하고,
기능 내부의 계층은 실제 복잡도에 따라 필요한 만큼만 분리한다.

## Result

```text
Single Spring Boot Application
├── Player
├── Match
├── Analysis
├── Community
└── Shared Infrastructure
```

각 기능은 같은 애플리케이션 안에서 동작하지만
외부 API, 영속성, 애플리케이션 로직의 책임을 가능한 한 분리한다.

## Reason

- 초기 개발과 배포가 단순하다.
- 단일 DB 트랜잭션을 활용하기 쉽다.
- 기능 간 리팩터링이 쉽다.
- 마이크로서비스의 네트워크/운영 복잡도를 피할 수 있다.
- 기능별 경계를 유지하여 코드가 하나의 거대한 결합 구조가 되는 것을 방지할 수 있다.
- 프로젝트의 핵심 학습 목표인 Backend 설계, 외부 API 연동, 데이터 처리, 테스트에 집중할 수 있다.

## Alternatives Considered

### Traditional Layered Monolith

프로젝트 전체를 다음과 같이 기술 계층별로 구성하는 방식이다.

```text
controller/
service/
repository/
entity/
```

장점:

- 익숙하고 초기 진입 장벽이 낮다.
- 작은 프로젝트에서는 단순하다.

단점:

- 기능이 늘어날수록 한 기능의 코드를 여러 최상위 패키지에서 찾아야 한다.
- Player, Match, Analysis, Community 간 경계가 코드 구조에서 약해질 수 있다.

따라서 최상위 구조는 package-by-feature를 우선한다.

### Microservices

기능별로 독립 서비스와 배포 단위를 구성하는 방식이다.

장점:

- 서비스별 독립 배포와 확장이 가능하다.
- 팀과 트래픽 규모가 커졌을 때 독립적인 운영이 가능하다.

단점:

- 서비스 간 통신과 장애 처리 복잡도가 증가한다.
- 분산 데이터 정합성 문제가 생긴다.
- 로컬 개발, 테스트, 배포, 모니터링 비용이 커진다.
- 현재 프로젝트 규모에서는 얻는 이점보다 복잡도 증가가 크다.

현재 단계에서는 선택하지 않는다.

## Consequences

### Positive

- 하나의 애플리케이션으로 빠르게 개발할 수 있다.
- 모듈 간 경계를 유지하면서도 리팩터링 비용이 낮다.
- 테스트와 로컬 환경 구성이 단순하다.
- 향후 실제 필요가 생긴 모듈을 서비스로 분리할 가능성을 남긴다.

### Negative / Trade-offs

- 모듈 경계는 네트워크가 아니라 코드 규칙에 의해 유지되므로 개발자가 의존 방향을 지켜야 한다.
- 하나의 배포 단위이므로 특정 기능만 독립적으로 배포할 수 없다.
- 잘못 관리하면 시간이 지나며 일반적인 거대 Monolith로 변할 수 있다.

## Revisit Conditions

다음과 같은 상황이 실제로 발생하면 일부 모듈의 독립 서비스 분리를 검토한다.

- 기능별 독립 배포 요구가 반복적으로 발생한다.
- 특정 기능의 확장 요구가 다른 기능과 크게 다르다.
- 단일 애플리케이션 장애 범위가 운영상 문제가 된다.
- 팀이 기능별로 분리되어 독립적인 개발/배포가 필요하다.
- 비동기 데이터 처리 규모가 단일 애플리케이션에서 관리하기 어려워진다.

단순히 서비스가 성장할 가능성이 있다는 이유만으로 미리 분리하지 않는다.
